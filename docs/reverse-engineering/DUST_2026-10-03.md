Tracking issue: #26

## Verified public behavior

The Reddit launch describes Dust as a music visualizer and social listening experience intended to give songs, including AI-generated songs from tools such as Suno and Udio, a visual stage.

The public nanodot landing surface states that:

- a song becomes a live light show;
- forty thousand points respond to beats, sections and drops;
- song words and pictures can be drawn into the visual field;
- users can play shelf songs, add a song with lyrics, share a link, or embed it;
- an account is not required for those stated core flows;
- Dust Live is a synchronized room in which listeners hear the same song at the same moment, with the same visual dance and adjacent chat;
- the public compatibility statement names Chrome, Edge and Safari 26 across computer, phone and tablet;
- the visible top-level product labels include Stories and Music.

At the time of this research, the supplied Reddit thread had no visible user comments. There is therefore no comment-derived feedback to turn into requirements yet.

## What is not verified

The public evidence does not establish Dust's private implementation stack, rendering algorithm, shader code, beat/section detection algorithm, persistence model, upload pipeline, moderation system, feed-ranking logic, chat protocol, database, hosting provider, or exact synchronization architecture. No public upstream source repository was identified from the supplied post or public site during this audit.

Those internals must not be guessed and are not parity claims.

## Product mapping

Dust is a capability donor into Afterlight Radio rather than a second overlapping music product.

It is adjacent to RE-101 Tunedaway but not a duplicate:

- RE-101 separates room/audio state from visual-view state and adds immersive display controls.
- RE-379 adds audio-reactive rendering, local-song audition, shareable visual-story state and, later, synchronized/social listening.

The implementation is stacked on RE-101 draft PR #25 so it can reuse the already-tested visual-state, display and reduced-motion boundaries. It must be rebased onto `main` after PR #25 is resolved.

## Clean-room phases

### Phase A — reactive listening stage

Implement an original Afterlight canvas renderer attached to the existing first-party audio transport. The first slice intentionally uses a bounded number of Canvas 2D particles rather than claiming Dust's stated 40,000-point implementation or its exact beat/section/drop behavior.

Required behavior:

- explicit Reactive stage on/off control;
- original Halo / Drift / Pulse looks;
- analyser-driven energy response while preserving the current source and playback position;
- pointer-inert decorative canvas;
- reduced-motion / low-power behavior;
- local audio audition with browser `File` + object URL only;
- no raw local audio upload or network transmission;
- local filename remains UI-only and is not sent through analytics;
- leaving local audition restores the canonical room track;
- desktop and mobile browser verification.

### Phase B — shareable visual stories

Add a versioned descriptor for first-party room, track, reactive preset, optional bounded caption and allowed visual metadata. Sharing serializes only that descriptor. The renderer rejects unknown presets, oversized captions and unsafe URLs. Local file bytes and local filesystem metadata are never placed into a share link.

### Phase C — authenticated social / live listening

Only after persistence and moderation are designed and tested:

- story publishing, reactions and saves;
- report, block, delete and export;
- rate limits and abuse controls;
- synchronized room session protocol with authoritative timeline and reconnect behavior;
- bounded chat with moderation/audit controls;
- deterministic/explainable feed ordering before any recommendation-model work.

### Phase D — governed creator uploads

Public creator audio requires explicit rights/provenance, size/type validation, safe storage, transcoding, moderation, takedown and deletion flows. AI-assisted/AI-generated tracks need provenance fields. Provider names such as Suno/Udio are not treated as automatic redistribution or commercial-use clearance; then-current terms must be checked at the time of implementation.

## Phase A privacy and safety boundary

- no microphone permission;
- no hidden autoplay;
- no audio fingerprinting identity use;
- no third-party music scraping;
- no local file upload;
- no local filename analytics;
- no production/social-parity claim from repository-only evidence.

## Acceptance evidence

1. Source-contract check proves the reactive runtime has no network/upload primitives.
2. Build injects the reactive runtime on every room route.
3. Desktop Chromium and mobile WebKit prove stage toggle/preset changes do not change the active first-party source or interrupt playback.
4. Browser test proves local file audition uses a `blob:` URL and its distinctive filename is absent from outgoing requests.
5. Browser test proves returning from local audition restores the room track.
6. Reduced-motion mode is verified.
7. Exact-head hosted CI must pass before Phase A is marked verified.
8. Hosted Preview/manual visual review remains a separate gate and must not be claimed until actually run.
